# Save-conflict fix: own-save rebase instead of guessing

Status: proposal, 8 Oct 2026. Risk class: 🔴 (save path, customer-data integrity: MODEL-POLICY §8).
No code written. Design by Opus; implementation is meant for a Sonnet session, followed by an
Opus review of the diff (MODEL-POLICY §3).
Destination: `Desktop\jewelos\docs\save-conflict-fix-design.md`. The HANDOFF entry is separate.

Scope: the `_unconfirmedSaveIds.indexOf(...)` branch of `saveToCloud()` in `js/01-sync-core.js`
(about line 382), plus the two standing risks logged in HANDOFF on 8 Oct, since this fix
depends on them (section 7). Tanish's interim decision (Option A, keep reporting "saved") is not
reopened here. This document replaces that trade-off; it does not argue it again.

---

## For Tanish, in plain words

When a save's answer gets lost on a bad connection, the phone can't tell whether the save went
through. Today, if a *later* save then bumps into that earlier one, the app assumes the later save
was "the same thing again" and says "saved" without sending it. Usually that's true (you tapped
Save again). Sometimes it isn't (you did something different), and then that later work is
silently lost.

The fix stops guessing. When the phone can prove that the only thing that changed in the cloud is
its *own* earlier save, it sends what is on your screen right now, on top of that earlier save.
What you see is then what gets saved, every time. No duplicate bill, and nothing gets dropped
without you knowing. No database or server change is needed.

---

## 1. Root cause

### What the client knows when a conflict arrives

`store_cas_write` (`supabase/migrations/002_atomic_transactions.sql`) replaces the whole blob only
when `_v` matches `expectedVersion`. If it doesn't match, store-proxy returns
`409 {conflict:true, data: <entire stored blob>}` (`store-proxy/index.ts` lines 244-245). So
the client receives:

- `data._saveId`: the id of whoever wrote last
- `data._v`: the current version
- the full landed content

### Why the two cases look the same

Case 1 (resubmit) and case 2 (an unrelated later action) produce **the same evidence**:
the stored `_saveId` belongs to an earlier, failed `saveToCloud()` call from this tab, and the
current call's payload is different from what landed.

- **Ids can't separate them.** `_unconfirmedSaveIds` records *that* an attempt happened, not
  *what it was for*. Both cases match the list.
- **Content can't separate them either.** This is the important finding. A "resubmit" is not a
  byte-identical retry. After the first call fails, `_commitSaleTransactionNow` rolls the sale
  back (`02-ui-inactivity-modals.js` lines 1683-1716), and the user's second tap mints a **new**
  invoice number from the server counter (`allocInvNo`), new timestamps, and new audit and
  stock-movement ids. Hashing the payload, or comparing it with the landed blob, would classify
  every real resubmit as "different". That is the same failure as the reverted 8 Oct attempt,
  reached by another route.
- **Only the user knows** whether the second tap meant "same sale again". No field in the blob
  carries that intent, and the app has ~40 `saveToCloud()` callers with no shared notion of
  "logical action".

So the current design can't be made to tell the two cases apart from the data it has. The
branch has to choose a failure mode, and that is the dilemma Tanish was asked about.

### Two smaller defects in the same branch today

- In case 1 the user sees `"✅ Sale recorded! Invoice: N+1"` (from the *resubmit's* `sale.invNo`),
  while the reload just put sale **N** (the landed one) on screen. The toast and the data disagree.
- The branch does not check `data._v`. It never confirms that the matched save is the *only*
  write since this tab's base version.

## 2. The key observation that removes the dilemma

You don't need to tell case 1 from case 2 if one action is correct in both.

Take any conflict where:

- (a) `data._saveId` was generated by **this tab's** `saveToCloud()` (in memory, not read back from
  localStorage), and
- (b) `data._v === expectedVersionThisAttemptSent + 1`.

Then the stored blob is exactly *(this tab's base version) + (its own earlier attempt's delta)*.
Nothing from any other device is in it: any other writer stamps its own `_saveId`, and the CAS
lets in exactly one write per version. Calls are serialized by `isSaving` (once the watchdog is
fixed, section 7), so the earlier call has **already finished** when the current one runs: its
callback fired and its caller either kept or rolled back its change in `S`. **`S` is therefore
precisely what the user has been told is true**, and the only cloud content it would overwrite is
that earlier attempt, which the user was told failed.

So the correct move in both cases is to **rebase**: re-send this call's payload with
`expectedVersion = data._v`.

| | Today (Option A) | Rebase |
|---|---|---|
| Case 1: resubmit after an answer was lost | One sale (N) in the cloud; toast says N+1 | One sale (N+1) in the cloud; toast says N+1 |
| Case 2: unrelated later action | **Later action silently lost**; earlier "failed" sale reappears | Later action saved; earlier sale stays rolled back, as the user was told |
| Duplicate bill? | No | No |

After a rebase, the cloud is in exactly the state it would be in if the earlier attempt had
genuinely failed. Every caller's rollback path is already designed for that state: invoice-number
gap from a consumed counter value, restored `nextSaleId`/`nextInvNo`, stock snapshot restored.
No new state is introduced.

## 3. Options considered

### Option 1: per-action idempotency key (truly distinguishes case 1 from case 2)

**How:** each form mints an `actionKey` when it opens and reuses it on "tap to retry" (F4 forms
stay open). Every `saveToCloud(callback, {actionKey})` sends it, and the blob records the
last N applied keys (`_appliedKeys`). On a conflict, "same key landed" means case 1 (load and
report saved); a different key means case 2 (rebase or fail).
**Changes:** client (every caller, ~40 sites across 9 files) and the blob shape. The server can
stay a pass-through, or check keys inside `store_cas_write` (migration).
**Data impact:** a new capped array in the blob; old blobs without it count as "no key".
**New failure modes:** any caller that forgets the key falls back to today's ambiguity, with no
signal. Forms that close and reopen mint a new key, so a genuine "redo from scratch" counts as
different. The only thing it buys over rebase is keeping invoice N instead of N+1 in case 1.
**Verdict:** rejected. It costs the most, it's the easiest place to introduce a bug, and the
result is no better for data integrity than rebase.

### Option 2: content hash / payload comparison on conflict

**How:** hash the payload (minus `_saveId` and `_v`) and compare it with the landed blob.
**Changes:** client only, or the server returns a hash instead of the full blob.
**Verdict:** rejected. It doesn't work: a resubmit is never content-identical (new invoice
number, timestamps, ids; section 1). The only identical-payload case is a retry *within one
call*, and the existing `data._saveId === saveId` branch already handles that exactly.

### Option 3: three-way merge (apply this call's delta on top of the landed blob)

**How:** keep a snapshot of the last-loaded blob, diff `S` against it per collection and record
id, and apply that delta onto `data`.
**Changes:** client only, but large: ~15 collections, counters, `dayBook`, `rates`, capped logs.
**Verdict:** rejected. Counter and stock merges are calculation-correctness risks (§9 #2), and
the effort is large for a rare path. It's also unnecessary: (b) above guarantees there is nothing
foreign in `data` to merge.

### Option 4: scope or TTL `_unconfirmedSaveIds`

**How:** expire ids after X seconds, or key them by record.
**Verdict:** not worth doing, neither alone nor alongside the fix. Case 2 isn't about *stale*
ids. It can happen 10 seconds after the failed call (60 s timeout, then the user's next tap).
A TTL short enough to matter would also expire ids for legitimate late landings and send
those down the "real conflict, redo your last action" path, which invites duplicates. Under
rebase, an id's age doesn't matter because the `_v` check makes membership safe. The 20-entry
cap stays as it is.

### Option 5 (recommended): own-save rebase, client only

See section 4.

## 4. Recommended approach: own-save rebase

### The rule

On a 409 conflict, check these branches in order:

1. `data._saveId === saveId` (this call's own earlier attempt landed): **unchanged**, `_done_ok`.
2. **NEW: rebase.** `data._saveId` is in `_unconfirmedSaveIds` (this tab's memory only),
   **and** `data._v === callVersion + 1`, **and** this call hasn't rebased yet. Set
   `callVersion = data._v`, rewrite the C2 marker to the new version, log one audit line, then
   `attempt()` again. This doesn't count against the 3 retries.
3. `data._saveId === _pendPushId` (the id read back from the localStorage C2 marker after a
   reload): **today's behaviour, unchanged.** Load the cloud, report saved, show the
   "earlier save had gone through" toast.
4. Anything else: real conflict, **unchanged.**

### Why branch 3 keeps today's behaviour, and why that's safe

After a reload, the tab has no memory of its earlier calls. `S` comes from the cache, and the
push isn't a user action; it's a background re-send. Every `saveToCloud()` rewrites the marker
with its **own** id, so the marker always names the newest attempt. "Landed id == marker id"
therefore means the cloud already holds this device's newest attempt. Loading it drops nothing
silently. At worst a rolled-back record reappears, and the existing toast already says so. Not
rebasing here also avoids a new multi-tab hazard: tab 2 reads tab 1's marker (shared
localStorage), and if it rebased, it would overwrite tab 1's landed save with tab 2's own
in-memory `S`.

To make this split real, line 55's `_unconfirmedSaveIds.push(_pendSave.id)` becomes
`_pendPushId = _pendSave.id`.

### Does it eliminate the ambiguity or just shrink it?

**Within one tab, it removes the silent-loss failure entirely**, provided the watchdog fix
(section 7) holds: calls are strictly serialized, so (a) and (b) together prove the stored blob
is base + own delta. Nothing is guessed. Both cases get the outcome that matches the screen.

**What remains, all explicitly out of scope or pre-existing:**

- **Out-of-band edits to the `store` row** (Cowork has the live database). If someone edits the
  blob by SQL, bumps `_v` and leaves our `_saveId` in place, a client would rebase over that
  edit. Today that client would load it. **Rule for Cowork:** any manual write must set
  `_saveId` to something like `"manual-<date>"`. It must be in the HANDOFF entry.
- The multi-tab marker push in `loadFromCloud` (line 47-63) can already push a stale tab's `S`
  when the cloud is still at the marker's version. That hazard is pre-existing and unrelated.
  Note it, but don't fix it here.
- The diagnostics "Reset Save Lock" button (`08-girvi-viewmode.js:1478`) releases `isSaving` by
  hand and can create concurrency on purpose. It's a support tool and stays known-unsafe.
  (It also assigns `_saveLockToken`, a variable defined nowhere else, left over from the
  2 Oct lock-token arc. It's harmless, but worth a one-line cleanup some day.)

### Justification against MODEL-POLICY §9

1. **Preserve existing data.** Case 2 stops losing the user's latest action. What gets overwritten
   is only the user's own earlier save, which they were told failed and which was removed from
   their screen. That's the state a normal failed save leaves behind, and nothing else in the
   cloud is touched (proven by the `_v` check). One audit line records the overwrite.
2. **Correct calculations.** No merging. Counters, stock and day-book values come straight from
   `S`, the same as on any successful save. The invoice series gets the same single gap a normal
   failed sale leaves today.
3. **Backward compatibility.** No server, schema or blob-shape change. Old blobs, old clients and
   new clients interoperate. A not-yet-updated phone just keeps Option A behaviour.
4. **Transaction consistency.** It's still one CAS'd whole-blob write. The rebase is an ordinary
   CAS write at a known version.
5. **Testing.** Pure client logic, fully reachable by the existing `landedApp` /
   `earlierLandedApp` harness pattern.
6. **Safe migration.** There's nothing to migrate. Rollback is a one-commit revert.
7. **Auditability.** Each rebase adds an `S.auditLog` entry naming the overwritten save id and
   version.

### New tests required

1. **The bug itself (case 2).** Call A fails (every attempt rejects with "answer lost"). Then
   push a distinct record into `S.girvi` and call B. B's first PUT gets a 409 with stored
   `{_saveId: A's id, _v: base+1}`. Expect a rebased PUT carrying the new girvi record at
   `expectedVersion base+1`, `'saved'`, no GET. *This test fails on today's code*, which is
   what proves the fix.
2. **Version gap means a real conflict.** Stored `_saveId` is ours but `_v === base+3`. Expect

3. **Rebase happens at most once.** The rebased PUT gets 409 from another device. Expect
   `'version-conflict'`, exactly 2 PUTs on the call, and `_unconfirmedSaveIds` cleared.
4. **A rebased PUT whose answer is lost, then retried.** The retry's 409 carries this call's own

5. **A marker-sourced id is never rebased.** After a simulated reload (empty in-memory list),

6. **Risk #1: version captured per call.** Change `_loadedVersion` between attempt 1 and its

   `expectedVersion`.
7. **Risk #2: watchdog vs. a live chain.** Each `attempt()` re-stamps `_isSavingSetAt`.
   Advance a fake clock 35 s into a 60 s attempt and run the watchdog callback: `isSaving` must
   still be `true`. (The watchdog is a `setInterval` in `00-config-state.js`. Capture it the
   same way the harness already stubs timers.)
8. **Audit line.** After a rebase, `S.auditLog[0]` names the overwritten save id, and it's
   present in the rebased PUT's payload.

e2e: run `tests/e2e/failed-saves.spec.js` and `session-restore.spec.js` before and after the

  var landed = res.body && res.body.conflict && res.body.data;
  if(landed && !rebased && landed._saveId && _unconfirmedSaveIds.indexOf(landed._saveId) !== -1
     && landed._v === callVersion + 1){

## 7. Interaction with the two standing risks

**Both have to be fixed for the guarantee to hold. They're Steps 1-2 above: small, and in the
same batch.**

- **Watchdog shorter than the save chain (risk #2). Required.** The rebase proof assumes the
  earlier call had *finished* (callback fired, rollback applied) before the current one
  started. With a 30 s watchdog and 60 s attempts, a slow connection makes overlapping calls
  *likely*, not rare. With overlap, B's `S` still contains A's change. Rebase then writes A+B
  correctly, but A's retry later sees a foreign-looking id (B's), takes the real-conflict path,
  rolls A back and tells the user to "redo", which invites a duplicate. Rebase alone is still
  strictly better than today in the overlap case (today the same overlap silently loses B), so
  it isn't *harmful* without Step 1. But "fully eliminates" is only true with Step 1.
- **Stale `expectedVersion` on retry (risk #1). Required, for a different reason.** The `_v`
  check needs the version *this attempt actually sent*. Re-reading `_loadedVersion` per attempt
  (today) both causes the silent stale-overwrite that HANDOFF describes and makes `callVersion + 1`
  meaningless. With per-call capture, a load that runs mid-call makes the retry conflict
  *safely*: branch 1 if the load pulled in our own landing, branch 4 otherwise. It never
  overwrites silently.
- **Not required, but worth a follow-up:** making `loadFromCloud` wait while `isSaving` is set.
  Tab-switch (`02:155`), `online` (`08:1615`) and `forceSync` don't check it; the poll and
  `visibilitychange` do. After Step 2, that's a screen-freshness problem, not a cloud data-loss
  problem: `S` can show the loaded data while the cloud gets this call's payload, until the next
  load. Deferring means queued loads can pile up behind a 4-minute save. Leave it out of this
  batch unless the reviewer disagrees.

## 8. Risk and effort

**Size: small-medium.** About 25 changed lines of client code across two files, one updated test,
eight new tests, and zero server or schema work. Realistically one Sonnet session, including the
review loop.

**Risk: 🔴.** Every save in the app goes through this function. The change is narrow, and every
new branch requires preconditions that today's tests never produce by accident.

**Stop and escalate to Opus (MODEL-POLICY §3 step 3) instead of pushing on if:**

- Any test other than `...EARLIER call's landed save...` fails after Step 3 or 4, especially a
  C2 test.
- Step 2 breaks a test. That means something depends on `_loadedVersion` changing mid-call, and
  the risk-#1 analysis is incomplete.
- You find **any writer of the `store` blob other than `saveToCloud()` → store-proxy PUT**
  (another Edge Function, a migration that updates `data`, a Cowork script). The `_v` proof
  assumes there is none: `supabase/` showed only `store_cas_write` as of 8 Oct.
- You find a `saveToCloud` caller that, on failure, rolls back *only some* of what it changed
  (for example a record but not a counter or day-book total) **and** whose leftover must not
  reach the cloud. Rebase would publish that partial state, whereas today's "load landed" would
  hide it.
- The e2e baseline comparison shows a new deterministic failure in `failed-saves` or
  `session-restore`.
- The reviewer argues that overwriting a landed-but-reported-failed record is unacceptable for a
  specific record type (Close Day, girvi closure, purchase-to-stock). In that case, Option 1
  (idempotency keys) becomes the fallback for that type only. Don't improvise a merge.
